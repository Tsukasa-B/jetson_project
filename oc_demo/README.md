# oc_demo — OC(オープンキャンパス)来場者向けデモGUI

来場者が**曲を選んでSTARTを押すだけ**で、空気圧人工筋(PAM)ロボットが強化学習ポリシーで
リズムを叩く様子を、ブラウザ1画面（打楽器譜・目標力/実測力の波形・打点判定・スコア）で
見せるデモです。中身は Python標準ライブラリ + 既存の numpy/onnxruntime/pyserial のみで
書かれており、`src/` `IROS/` `tools/`（jetson_project 本体）には一切手を入れず、
`oc_demo/adapter.py` を唯一の結線点として本体の実装を参照します。

このドキュメントは `oc_demo/` の実装を実際に読んで書いています。以後 `oc_demo/*.py` を
変更した場合、特に「設計メモ」章の前提が崩れていないか（`oc_demo/parity_check.py` が通るか）
を都度確認してください。

## 当日チートシート（まずここだけ読めばOK）

**起動（コンテナの中で、`jetson_project/` 直下）:**
```bash
./run_oc_demo.sh --mock      # 練習・画面確認だけ（ロボットに触らない）
./run_oc_demo.sh --verify    # センサは読むが圧力0固定（ロボットは動かない）
./run_oc_demo.sh             # 本番。ロボットが動く
```

**ブラウザを開く:** `http://localhost:8080/`（同じLANの別PCからは `http://<JetsonのIP>:8080/`。
起動ログに実際のIPが出ます）。会場のJetson本体では全画面表示:
```bash
chromium-browser --kiosk "http://localhost:8080/?scale=1.3"
```

**止め方:** 画面の「■ ストップ（緊急停止）」はいつでも押せます。押すと圧力0が2回送られ
制御ループが止まります。サーバごと止めるときは `Ctrl+C`。

**困ったら:**
1. 右上バッジで今どのモード（デモ/駆動なし検証/実機）か確認
2. `curl -s localhost:8080/api/health` が返るか確認
3. 「トラブルシューティング」章の表を見る
4. それでも分からなければ `oc_demo/parity_check.py` と `python3 -m oc_demo.check_serial` /
   `python3 -m oc_demo.check_models` の出力を持って相談する

## 使い方

### 起動モード3段階

| モード | コマンド | 何が起きるか |
|---|---|---|
| モック | `./run_oc_demo.sh --mock` | シリアルに繋がない。`oc_demo/plant.py::MockPlant` が仮想の物理応答を返す。画面確認・練習用 |
| 駆動なし検証 | `./run_oc_demo.sh --verify` | 実シリアルに繋いで実センサを読み、ONNX推論もするが、送る圧力は常に0(`RunConfig.drive=False`)。ロボットは動かない |
| 実機 | `./run_oc_demo.sh` | 本番。ロボットが動く |

右上のバッジに「デモ（シミュレーション）/ 実機・駆動なし検証 / 実機モード」が出ます。
今どれで動いているかは必ずそこで確認してください。

### コンテナの起動

```bash
sudo docker run --runtime nvidia -it --rm --network host \
    --device /dev/ttyUSB0 \
    -v /home/okuilab/jetson-containers/data/jetson_project:/data/jetson_project \
    -w /data/jetson_project \
    my_ros2_pytorch_container:latest bash
```
実機を繋がず練習だけするなら `--device /dev/ttyUSB0` の行は外してよい（README.md ルート
参照）。`--network host` なので `docker run` に `-p` オプションは不要です。

### ホスト側で必要な下準備（実機を使う場合）

```bash
sudo modprobe ftdi_sio
echo 0584 b050 | sudo tee /sys/bus/usb-serial/drivers/ftdi_sio/new_id
ls -l /dev/ttyUSB0     # 出てくることを確認
sudo date -s "2026-07-31 12:00:00"   # Jetsonは時計が狂いやすい。ログ名がunixtimeなので先に合わせる
```

### ブラウザの開き方（3通り）

1. **Jetson本体で全画面表示（会場用）**
   ```bash
   chromium-browser --kiosk "http://localhost:8080/"
   ```
2. **同一LANの別PC・タブレットから**
   起動ログに `[oc_demo] 同じLANの別PCからは: http://<IP>:8080/` が(複数IPがあれば全部)
   表示されるので、そのURLをそのまま開く。Jetsonと同じネットワークに繋がっている必要がある。
3. **VSCodeのポート転送（開発機から）**
   VSCodeの「ポート」パネルで `8080` を追加 → 転送されたURL（`http://localhost:xxxxx`）を開く。
   `--network host` でコンテナを起動していれば、Jetson側のポートがそのまま見える。

**開けないときの確認順:**
- Jetson上で `curl -s localhost:8080/api/health` が返るか（返らなければサーバ自体が
  落ちている/起動していない）
- 別PCから `ping <JetsonのIP>` が通るか（通らなければネットワーク的に見えていない）
- 会場のWi-Fiがクライアント間通信(AP client isolation)を禁止していないか（施設・NW管理者に確認。
  isolationが有効だと ping すら通らない）
- Jetson側でファイアウォール(ufw等)が有効なら `8080/tcp` を許可

### UIの拡大率を変える

会場後方からでも文字が読めるよう、2通りの手段を用意しています（`oc_demo/static/index.html`）。

- **URLパラメータ**: `http://localhost:8080/?scale=1.3` — kiosk起動コマンドに埋め込んで
  当日の基準値を固定する用
- **キーボードショートカット**: `Alt` + `+` / `Alt` + `-` でその場で0.1刻みに調整、
  `Alt` + `0` で100%に戻す。会場で気づいたときに即座に直す用（リロード不要）
- 範囲は0.7〜2.0。変更すると画面右上に一瞬「拡大 130%」のように表示され、
  その右の常時表示の小さな数字（`拡大 100%`など）で現在の実効値がいつでも確認できる
- 内部実装は `<html>` の CSS変数 `--ui-scale` を `font-size: calc(18px * var(--ui-scale))`
  に反映し、ボタン高さ・パディング・文字サイズなど中身の寸法をすべて`rem`で書くことで
  一括拡大する方式（**`zoom`は使っていない**。`zoom`だと`100vh`/`100dvh`の実寸ごと
  拡大されてしまい、画面の外枠自体がはみ出す不具合があったため）。外枠(ヘッダ/メイン領域の
  縦分割、Canvas領域/下部カードの縦分割)は`vh`/`dvh`ベースのまま固定し、拡大率を上げると
  文字とボタンが大きくなった分だけCanvas領域(`.rollwrap`)が押し縮められる
- Canvas領域には`min-height`（画面高さの28%または140pxの大きい方）を敷いてあり、
  拡大しすぎてこれを割り込みそうな場合、または下部の「テンポ/START/STOP」ブロック
  (`.asideFixed`)が画面下端をはみ出しそうな場合は、**拡大率そのものを自動的に
  頭打ちにする**（例: 1366×768のような小さい画面でAlt+を押し続けても、
  ある時点で拡大が止まる。実効値は右上の表示で常に確認できる）
- 曲リスト(`.songsScroll`)だけは独立してスクロールする作りになっており、曲数が
  増えても・拡大率を上げても、**STOP（緊急停止）ボタンだけは画面外に押し出されない**

### 環境変数・起動引数

`run_oc_demo.sh`（ラッパー。中身は変更していません）:

| 環境変数 | 既定値 | 効果 |
|---|---|---|
| `OC_MODEL` | `IROS/modelB.onnx` | 実機/検証モードで使う既定モデル(`models/`からの相対パス) |
| `OC_SERIAL_PORT` | `/dev/ttyUSB0` | シリアルポート |
| `OC_HTTP_PORT` | `8080` | HTTPポート |

`run_oc_demo.sh` は `--midi-dir midi` 固定で `python3 -m oc_demo.server` を呼びます。
`songs/` も同時に読み込みたい・ポート以外の細かい設定を変えたい場合は、ラッパーを介さず
直接サーバモジュールを呼んでください:

```bash
python3 -m oc_demo.server \
  --midi-dir midi --midi-dir songs \
  --models-dir models \
  --model IROS/modelB.onnx \
  --port-name /dev/ttyUSB0 \
  --bpm-min 60 --bpm-max 180 \
  --http-port 8080 \
  --mock            # 省略すると実機、--no-drive で駆動なし検証
```

| 引数 | 既定値 | 説明 |
|---|---|---|
| `--midi-dir`（複数回指定可） | `midi`（`OC_MIDI_DIR`をカンマ区切りで指定も可。両方省略時は`midi`単体） | MIDI置き場。複数指定すると曲一覧が出どころごとにグループ表示される |
| `--models-dir` | `models` | `.onnx`を探すディレクトリ |
| `--port-name` | `/dev/ttyUSB0` | シリアルポート |
| `--model` | なし | 既定モデル(未指定だと`ScriptedPolicy`＝学習済みでない素朴な動作になる) |
| `--mock` | オフ | 実機に繋がずシミュレーションで動かす |
| `--no-drive` | オフ | 実シリアルに繋ぐが圧力0だけを送る(駆動なし検証) |
| `--bpm-min` / `--bpm-max` | `60` / `180` | UIで選べるBPMの範囲 |
| `--host` | `0.0.0.0` | バインドアドレス |
| `--http-port` | `8080` | ポート |

## 曲の入れ替え

### MIDIをどこに置くか

- `midi/` … OCデモ本番用。`oc_demo/tools/make_demo_midi.py` で生成した5曲が入っている
- `songs/`（jetson_project直下、既存） … ロボット自身の研究検証用MIDI。全曲**単一ピッチ・
  同時打ちなし**で機構的には互換だが、長さ(21〜43秒)や曲調がOCデモ向けではないものが多い。
  `--midi-dir midi --midi-dir songs` で両方読み込むと「上級者向け」枠として出せる

`.mid`ファイルを増やすだけなら、上記どちらかのディレクトリに置いて起動し直すか
`POST /api/reload` を呼べば読み直します。

### 片腕ロボットで演奏可能な条件

- **単一ピッチのみ**（打面は1つしかない。複数ピッチのMIDIを読ませても叩き分けはしない）
- **同時打ちなし**（和音は不可。ノートが重なっていると片方が無視される想定はしていないので
  事実上の未対応 = 予期しない挙動になり得る）
- **打点間隔の下限**: 実機ログ(`IROS/deploy_results/modelB/*.csv`)で実証済みの最短間隔は
  81〜84ms(BPM138〜170の8分音符)。それより詰めると機構的に追従できない可能性がある。
  デモの「ダブルストローク」パターンは100ms間隔でこの限界に近づけて作ってある

### labels.json の書き方

各MIDIディレクトリ直下に置く。曲名(拡張子抜きのファイル名)をキーにした辞書で、
値は文字列（表示名のみ）か `{"label":..., "note":...}`（表示名+一言説明）のどちらでも良い:

```json
{
  "01_quarter": {"label": "四分打ち（かんたん）", "note": "まず基本の四分打ち。"},
  "02_eighth": "八分打ち"
}
```

### デモ用リズムの再生成

```bash
python3 -m oc_demo.tools.make_demo_midi
```
`oc_demo/tools/make_demo_midi.py` が5パターン(四分/八分/三連符/シンコペーション/
ダブルストローク)を標準ライブラリのみで生成し直し、`midi/labels.json` も一緒に上書きします。
実行結果として各パターンのBPM・打数・長さ・最小打点間隔が表示されるので、変更した場合は
必ず出力を確認してください（min_gap_msが極端に短くなっていないか＝機構的に無理なパターンに
なっていないか）。

## 実機立ち上げ手順

**この順番で。いきなり `./run_oc_demo.sh` を実行しないこと。**

### Step 1. 受信の健康診断（送信なし・ロボットは動かない）
MicroLabBoxのSimulinkを動かし、**スティックが打面に触れていない**ことを確認してから:
```bash
python3 -m oc_demo.check_serial --seconds 10
```
見るのは2つ:
- 受信レートが200Hz近くあるか
- **force_Nの中央値が0付近か**。**ここが±30ms判定の信頼性に直結します。** -20N付近など
  大きくズレている場合は、配線/アンプ/Simulink側スケールの問題を切り分けてから先に進むこと。
  ズレたまま進めると、当日の「タイミング成績」表示が意味を持たなくなります

### Step 2. モデルの入出力を確認（ロボットは動かない）
```bash
python3 -m oc_demo.check_models
```
使う予定のモデルのobs次元・lookahead・RNN有無が意図通りか。LSTMモデルで
「RNN入力はあるのに出力に状態が返っていない」と出たら、そのまま動かすと毎ステップ
h/cがゼロ＝記憶なしで動いてしまうので要修正。

### Step 3. 駆動なしで通し（ロボットは動かない）
```bash
./run_oc_demo.sh --verify
```
ブラウザで1曲スタートし確認:
- 右上バッジが「実機・駆動なし検証」
- `curl -s localhost:8080/api/health` の `adapter.target_force` が `real:...`
  になっている(`fallback:`ではない)
- **力センサのゼロ点**（画面左下 `力ゼロ点 x.xxxN`）が妥当な値か
- 最後まで例外なく `finished` になる

### Step 4. 実駆動
```bash
./run_oc_demo.sh
```
最初は遅いテンポの1曲から。開始前に:
- 周囲に人・物がないか
- 物理の非常停止（元栓/電源）に手が届く位置にいるか
- 画面の「ストップ（緊急停止）」が押せる状態か → まず押して効くことを確認

## 画面の見方（来場者への説明用）

- **音符（楽譜）** = お手本のリズム。右から左へ流れてきて、画面中央の白い縦線に来た瞬間が
  「叩くタイミング」
- **青い山（波形）** = そのとき出したい力の大きさ
- **黄色い線** = 力センサが実際に測った力
- **緑/赤の点** = 実際の打点。緑は楽譜から±30ms以内、赤はそれ以上ズレている
- **右下の%** = ±30ms以内に入った打点の割合

「人間のドラマーの許容ズレがだいたい±30ms程度」という前置きをすると伝わりやすいです。

## 設計メモ（後で触る人向け）

- **pip installが使えない環境**なので、`oc_demo/`は標準ライブラリ + 既存の
  numpy/onnxruntime/pyserialだけで書いてある。新しい依存を増やしたくなったら、まず
  標準ライブラリで書けないか考えること
- **テレメトリはWebSocketではなくSSE**(`/events`, `EventSource`)。サーバ側を
  `http.server`だけで書くための選択（WebSocketの実装が要らない）
- **`adapter.py`が既存`src/`との唯一の結線点**。`src/`側の実装が変わったら、まず
  `adapter.py`のimportとラップ部分だけを見ればよい設計
- **`midi_rhythm_port.py`は`src/midi_rhythm_generator.py`の移植**。後者はtorch/mido
  依存でpip不可環境では動かせないため、numpy + `oc_demo/midiparse.py`だけで同じ数式を
  再実装している。**ここを変更したら必ず`oc_demo/parity_check.py`を実行し、差が0.0の
  ままであることを確認すること**（実物との一致はここでしか保証されない）
- **obsは最新1フレーム、表示と打点判定は200Hz全フレーム**、という使い分けをしている。
  `src/deploy_policy.py`とのパリティ(観測ベクトルの再現性)を壊さないためにobsは
  必ず最新1フレームのみを使い、一方でテレメトリ波形描画・打点検出・力センサのゼロ点推定は
  取りこぼしを避けるため`SerialPlant.read_burst()`で得られる全フレームを使う
  （詳細は`oc_demo/runner.py`のコメント参照）
- **lookaheadの正規化は固定値`adapter.TARGET_FORCE_N`(=20.0N)を使う**。曲ごとの
  ピーク値で割ってはいけない。実物(`src/midi_rhythm_generator.py::get_state`)が
  固定のtarget_forceで正規化しているため、曲によって割る値が変わると学習済みONNX
  ポリシーに渡すlookaheadのスケールがズレて実際の打撃精度が落ちる（過去に実際に
  入っていたバグ）
- **論文E(frame stacking, obs 175次元)は未対応**。`oc_demo/policy.py::OnnxPolicy`が
  lookahead推定値が75stepを超えると明示的に例外を投げる（黙って誤ったobsを作らないため）
- **画面の情報の優先度**は「曲選択/START/STOP」＞「楽譜(音符)と再生位置」＞
  「タイミング成績%」＞「譜面ロール」＞「力の波形」＞「圧力3ch・関節角」の順(2026-07-31)。
  来場者(高校生・保護者)は少し離れて見る前提のため、力の波形はCanvas下部の薄い帯
  (`ROLL_RATIO=0.68`、`static/index.html`の`draw()`参照)に留め、圧力3ch・関節角は
  数値が読めれば十分という判断で1枚のカードに統合してある(`.strip .card:nth-child(1)`
  内の`.monogrid`)。新しい表示要素を足す時もこの優先度を崩さないこと

## 調整ポイント

どこを変えると何が変わるか（すべて`oc_demo/runner.py::RunConfig`のデフォルト値）。

| パラメータ | 現在値 | 変える基準 |
|---|---|---|
| `force_threshold_N` | `5.0` N | 打点判定のしきい値。実データ(`IROS/deploy_results/modelB/*.csv`)で無負荷ノイズの標準偏差が0.27〜0.52N、実打撃ピーク平均13〜19Nだったことから、ノイズの10倍以上・ピークの1/3以下になるよう設定。会場のセンサ個体差でノイズが大きい/小さい場合はこの比率を目安に調整する |
| `hit_refractory_s` | `0.05` s(50ms) | 同一打の減衰ノイズを2打として誤カウントしないための不応期。実データで確認した誤カウント間隔が10〜20msだったため、デモ曲最速パターン(ダブルストローク,100ms間隔)より十分短い値にしてある。新しいデモ曲で間隔がこれより詰まるなら、その曲の再現性が壊れるので要見直し |
| `force_limit_N` | `60.0` N | これを超えると安全停止しエラー表示。実際の異常か、力センサのゼロ点ズレかを`/api/health`の`force_zero`で確認する |
| `lead_in` | `1.5` s | 曲頭までのカウントイン。短くすると来場者の準備時間が減る、長くすると1人あたりの回転が悪くなる |
| BPM範囲(`--bpm-min/--bpm-max`) | `60`〜`180` | 学習時の範囲を超えないよう当日設定を絞ること。モデルを変えたら`models/manifest.yaml`の想定と照らして再検討 |
| 既定モデル(`OC_MODEL`) | `IROS/modelB.onnx` | 来場者にはモデル選択UIを出していないので、当日どのモデルで見せるかはこれで決まる |

## 安全

| 項目 | 実装 |
|---|---|
| 緊急停止 | 画面に常時「■ ストップ（緊急停止）」。演奏中(arming/running)でも常に操作可能(P0-2で確認済み)。押すと制御ループが抜けて圧力0を2回送信 |
| 異常力 | `force_limit_N`(既定60N)を超えると自動停止しエラー表示 |
| 終了時 | 正常終了・例外・停止のいずれでも`plant.close()`で圧力0を送る |
| ブラウザ切断 | 演奏は止まらない(画面が落ちてもロボットは曲を弾き切る)。**物理の非常停止は別途会場に用意すること** |
| 演奏中の操作ロック | BPMスライダー・曲選択ボタンは演奏中(arming/running)は無効化される。表示と実際の演奏テンポが食い違わないようにするため(P0-2) |
| BPM範囲 | `--bpm-min/--bpm-max`(既定60〜180)。学習範囲外に出さないよう当日設定を絞ること |

来場者に開放するのは「曲選択」「テンポ」「START」「STOP」だけです。モデル選択はUIに
出していません。

## トラブルシューティング

| 症状 | 見るところ |
|---|---|
| pipが通らない/`pip install`しようとしてしまう | このデモはpip不要。`oc_demo/requirements.txt`は説明文のみ。標準ライブラリ+numpy/onnxruntime/pyserialだけで動く設計 |
| 実機で1つも受信しない | `python3 -m oc_demo.check_serial`。baudは本番230400（`collect_data`系の115200とは別）。ホスト側で`modprobe ftdi_sio`/`new_id`をやったか |
| 力センサのゼロ点がずれる | `python3 -m oc_demo.check_serial`のforce_N中央値。-20N付近など大きくズレるなら配線/アンプ/Simulink側スケールの問題。oc_demoは開始時に自動でゼロ点を引く(`zero_force_window_s`)が、それは「その瞬間が無負荷である」前提。スティックが打面に触れた状態でSTARTすると丸ごとオフセットになる |
| GPUが使われない(`CPUExecutionProvider`のみ) | 調査済み。原因はインストール済み`onnxruntime`がCPU専用ビルドであること(`onnxruntime-gpu`ではない)。CUDA/cuDNN/TensorRT自体はコンテナに存在し`nvidia-smi`も正常。**結論: 対応不要。** modelBで0.11ms/step、20ms制御周期の1%未満で十分高速。GPU版onnxruntimeの入手にはネットワークが必要で現状の制約下では対応不可能でもある |
| ブラウザから開けない | 「使い方 > ブラウザの開き方」の確認順を参照。まず`curl -s localhost:8080/api/health`が返るか |
| ポートが埋まっている/実機モードのサーバが残っている | `./run_oc_demo.sh`を起動する前に必ず`ss -ltnp \| grep -E ':(8080\|8090)'`で誰かがそのポートを使っていないか確認すること。特に8080で実機駆動モード(`--mock`も`--no-drive`もついていない起動)のプロセスが残っていることがある(例: 実機テスト後に`Ctrl+C`し忘れた)。`/api/health`の`hardware`/`drive`が両方`true`ならそれは実機駆動モード。**自分が起動していないプロセスは絶対に停止しないこと**。見つけたら、それが誰の・何のためのプロセスか確認してから対応する(そのまま使う/持ち主に停止してもらう)。検証作業用に別ポート(例: 8090)を使う分には8080のプロセスに影響しない |
| 下部パネル(空気圧・関節角・タイミング成績)が見切れる | 修正済み(2026-07-31)。`static/index.html`のレイアウトをflex+`clamp(vh)`ベースに変更し、固定pxの高さ指定を撤廃した |
| `?scale=1.4`など拡大率を上げると下部が見切れる | 修正済み(2026-07-31)。以前は`zoom`で拡大していたため`100vh`/`100dvh`の実寸ごと拡大され画面からはみ出していた。`html{font-size:calc(18px*var(--ui-scale))}`+中身`rem`方式に変更し、外枠は`vh`のまま固定・拡大率が上がるとCanvas領域だけが縮む挙動にした。それでも小さい画面で拡大しすぎるとSTOPが隠れる場合は、拡大率の自動頭打ち(「UIの拡大率を変える」節参照)が働いているか確認する |
| ONNXが読めない/次元が合わない | `python3 -m oc_demo.check_models`。frame stacking付き(論文E)は未対応 |
| ロボットが動かない(実機のはず) | 右上バッジが「駆動なし検証」になっていないか。`--verify`/`--no-drive`を外す |
| ブラウザが真っ白 | `curl -s localhost:8080/api/health`が返るか。返るならブラウザキャッシュ、返らないならサーバログ |
| 曲が1つも出ない | `midi/`(または指定した`--midi-dir`)に`.mid`があるか。壊れたファイルは起動ログに`[score] skip ...`が出る |
| 演奏は動くがグラフが止まる | SSEが切れている。DevTools→Network→`events`が`pending`のままか確認。`EventSource`は自動再接続する |
| `力センサが xx N に達したため安全停止` | `force_limit_N`(既定60N)超過。ゼロ点ズレか実際の異常か切り分ける |
| MIDIのテンポが変に読まれる | `python3 -c "from oc_demo.midiparse import parse_midi; print(parse_midi('midi/xxx.mid')[1])"` |
| 打点が「出たり出なかったり」する(修正済み、再発時の確認用) | P0-1で対応済み。50Hz制御ループが200Hz受信の1/4しか見ておらず、幅10ms前後の打撃スパイクを取りこぼしていたのが原因（`oc_demo/plant.py::SerialPlant.read_burst()`で全フレームを見るよう修正）。UIの黄色い波形とMicroLabBox側の波形の山の数が一致するか目視で確認する |

## 既知の制限

- **論文E(frame stacking, obs 175次元)は未対応**。読み込もうとすると`oc_demo/policy.py`が
  明示的に例外を投げる
- **LSTMのh0/c0は演奏ごとにゼロ初期化**（1曲=1セッション運用。曲をまたいだ記憶の引き継ぎはしない）
- **同時打ち(和音)のMIDIは想定していない**。単一ピッチ・単音のみを前提に設計されている
- **ログのCSV保存はしていない**（`src/deploy_policy.py`のような実行条件JSON/CSVは出さない）。
  必要なら`oc_demo/runner.py::Runner.samples`/`subforce`を書き出す処理を足すこと
- **打楽器譜の休符記号はUnicode音楽記号(𝄽𝄾𝄿)を使用**。フォントによっては表示が崩れる
  可能性がある（未検証。会場のブラウザで一度目視確認すること）
- **`songs/`ディレクトリの曲は長さ・曲調がOCデモ向けに作られていない**（研究検証用のため）。
  上級者向け枠として出す想定で、主力は`midi/`の5曲
